Reinforce before departure

An expedition already committed to interrupting a public Beacon network can absorb one compatible local military formation before a departure. The ordinary merge pays one order, keeps the selected expedition and target, and cannot reduce current movement or exceed twelve ships. Any observed home threat vetoes the additional merge.

The preflight checks the actual weighted route with merged strength and one fewer order. It must preserve or improve the arrival estimate and retain orders for all currently available jumps on that path. No waiting, ship purchase, hidden-defense knowledge or altered declaration threshold is added. Actual combat still stops travel; peaceful first-contact continuation remains unchanged.

Why the new route must be checked

A separate synthetic case starts with a two-hop, one-cycle route. Adding strength lowers the perceived danger of an alternative enough that the policy prefers three hops over two. Movement is unchanged and the old route’s order check passes, yet arrival would slip to a second cycle. The preflight rejects that merge before payment. Independent review also checks that a weaker eligible partner can still be selected afterward.

Reproduction

The original engine and baseline commits remain in the merged Git history. Run the controlled comparison into a separate directory:

node scripts/expedition-reinforcement-benchmark.mjs --out /tmp/expedition-reinforcement-results

For historical reconstruction, copy design/ to a scratch directory, then run node reconstruct.mjs, node feasibility.mjs, node known-route-check.mjs and node eta-preflight-counterexample.mjs there. Those scripts deliberately write their derived outputs beside themselves; copying preserves the frozen evidence. The independent reports give their own reproduction commands.
